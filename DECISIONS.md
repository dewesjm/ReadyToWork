# Decisions

## 2026-10-30

- **Mockup, not production.** The project is a clickable mockup to present to users. No
  backend; fake data only. The user will build the real system integrations separately.
  Built so the real app can grow out of it (real logic, mocked data behind interfaces).
- **Angular** over React. Both would work; the deciding factor is that the team already has
  Angular pipeline templates. The core logic is plain TypeScript, so the choice only affects
  the view layer.
- **Tailwind CSS + daisyUI** for styling. Requirement: free, well maintained, unlikely to be
  paywalled. daisyUI is MIT, pure CSS and framework-independent; worst case it can be vendored.
  PrimeNG was ruled out (paid tiers). Open-core libraries in general avoided for the same
  reason. The tree component is built in-house since daisyUI has none.
- **PWA**, fully static, installable and offline-capable.
- **Admin settings stored in the browser** (no backend), behind a `SettingsStore` interface
  with a schema version, plus export/import JSON and reset to defaults.
- **Both layouts in the demo** (Dashboard and Drill-down), switchable, so users can choose.
- ~~**Grey (unknown) ranks above green**~~ (replaced below: Unknown status removed).
- **Hosted on Vercel** (user). Static site with clean URLs; `vercel.json` rewrites every path
  to `index.html` so deep links work.
- **Brand colors navy, white and gold** (user). Custom daisyUI theme as the default, plus a
  dark navy variant. Gold stays distinct from the amber "Expiring" color so status is never
  confused with branding.
- **Theme picker in an avatar menu** (user). Top-right button showing the viewer's initials;
  the menu lists the brand themes and all daisyUI built-in themes.
- **Code is a reference, not a starting point for the team's pipeline** (user). The mockup is
  for validating with business users; the team is not expected to reuse the code directly, so
  stock Angular CLI defaults are kept rather than matching the team's pipeline templates.
- **Angular 21 instead of 22.** Every Angular 22 release needs Node 24.15 or newer; the dev
  machine has 24.14.1. The user left the choice to Claude. Angular 21 runs on the current Node
  with no system change, and the version difference doesn't show in a mockup.
- **Scaffold defaults**: Angular CLI's Tailwind option (PostCSS), Vitest, zoneless, no SSR,
  component prefix `rtw`, 2025 file naming (`app.ts`, not `app.component.ts`).
- **Theme stored under `rtw.theme`** in browser storage, applied as `data-theme` on `<html>`.
  An inline script in `index.html` applies it before Angular starts to avoid a flash of the
  default theme. Unknown saved values fall back to the brand theme.
- **Neutral is slate grey in the brand themes**; navy is the primary color instead. (Neutral
  was also the "Unknown" status color until that status was removed.)
- **Brand PWA icons generated by a script** (gold ring and check on full-bleed navy, inside the
  maskable safe zone) instead of the Angular logo. The script isn't kept in the repo; the
  icons are placeholders until real branding exists.
- **One Readiness page instead of separate Org tree and Issues tabs** (user). The tree and the
  issues list have different jobs ("where are the problems?" vs "what do I fix today?"), but
  live on one page as a Tree / List switch sharing one toolbar, so filters carry over and
  there is one place to go. "Issues only" is a toggle switch in that toolbar, applying to both
  views. View and filters are kept in the URL (`/readiness?view=list&issues=all`).
- **Issues only defaults to on** (Claude's choice; easy to flip). Opening the page shows only
  what needs attention.
- **Service-based architecture** (user). Core logic is a set of small service classes
  (`StatusEngine`, `ProgramRules`, `RollupCalculator`, `OrgIndex`, `ReadinessEvaluator`) that
  take their config through the constructor and have no Angular imports. Angular wires them
  up with dependency injection next to `DataSource`, `SettingsStore` and `Clock`. Screens only
  talk to services.
- **An item is valid through its expiry date** (user). "Expires Dec 1" is yellow (if inside
  its warning window) through Dec 1 and red from Dec 2. The warning window is set per
  category and adjustable.
- ~~**Expired stays red even when the source data is out of date**~~ (user; replaced below:
  out-of-date data no longer changes any status).
- **Program requirements merge into the existing check** (user). If a program requires an item
  the person already has a check for, that check gets an "also required by" note instead of a
  second row, so one problem is counted once. A required item the person doesn't hold becomes
  a red "missing" check in the item's own category.
- **Dates are 'YYYY-MM-DD' strings with UTC arithmetic**, and "today" is always passed in, so
  time zones and daylight saving can't shift a status and the demo clock can move today.
- **Device check-in defaults**: 14 days without a check-in is yellow, 30 is red (config).
- **Program checks live in the required item's category** (e.g. a missing required
  qualification shows under Qualifications, marked "required by Program XYZ"), rather than
  in a separate "Program requirements" category. Whether the person view also gets a
  Programs summary tile is left for M4.
- **Device check-in uses "valid through" too**: day 29 without a check-in is the last yellow
  day; day 30 is red with 1 day overdue.
- **Scope pick lists on the Readiness page** (user, on trial). A Supervisor list ("people
  under [You]") and a Program list ("All programs") that combine. The user will judge it once
  it can be clicked.
- **Keyword search filters the page's results** (user) instead of jumping to one person:
  names, titles, employee IDs~~, and item names in the list view~~. (Item names dropped
  2026-10-31 when the list became one row per person; since then a search also pauses Issues
  only.)
- **Default scope lives under Preferences in the avatar menu** (user), next to the theme.
- **Fake dates are relative to the real date** (user). The generator builds every date from
  the day the demo is opened, so it looks the same whenever it's shown; the demo clock starts
  on the real date.
- **People carry an employee ID** so keyword search can match it.
- **DataSource and SettingsStore are asynchronous** (Promises), like a real API, so screens
  don't change when the mock is swapped out.
- **Fake org hits its status mix by design**: each person gets a target status first (planted
  scenarios, then weighted sampling so some crews are clearly worse), then records are
  generated to produce it. Default seed gives 201 people at 70/18/9/3% (73/18/9 since Unknown was removed).
- **Planted scenarios**: a crew with expired tool calibrations (the Foreman persona's crew),
  a crew whose SAP passwords expire in 6-9 days, and one green person who lacks the crane qualification (assign Crane Operations in
  Admin to turn them red).
- **Personas**: Foreman (tool-crew foreman), Superintendent, Director, and Admin (the director
  with admin rights, so admin sees everyone). (General Foreman added 2026-10-31.)
- **Settings shape**: one JSON object (`schemaVersion`, programs, assignments by person,
  warning-window overrides by category, preferences) under browser key `rtw.settings`.
  Imports are checked field by field with readable errors; missing sections fall back to
  defaults; older files are upgraded one version at a time through a migrations table.
  Unreadable saved data falls back to defaults rather than breaking the app.
- **Swappable seams are injection tokens with mock defaults** (`DATA_SOURCE`, `SETTINGS_STORE`,
  `CLOCK`, `DEFAULT_SETTINGS`). The real app overrides them in `app.config.ts`; services and
  screens don't change.
- **The demo date override is a saved preference** (`demoToday`), so a presenter's moved date
  survives a reload; Reset clears it. The theme is now a saved preference too (the separate
  `rtw.theme` key is gone).
- **Default persona is the Foreman** (first in the list), so the app opens as a foreman would
  see it.
- **M3: category and status filters only apply with Issues only on** (user). They define what
  counts as an issue ("Issues only, for SAP, not ready"); with Issues only off everyone in scope
  is shown and the filters are disabled. (Since 2026-10-31 they also pause during a search.)
- **M3: manager roll-ups always count everyone below** (user), whatever is filtered, so the
  numbers are always true. Filters only change which rows show.
- **M3: the tree opens down to foremen** (user) when Issues only is off and there is no search:
  managers of managers start expanded, crews start collapsed. Issues only and keyword search
  open every path to what they show.
- **Icons are inline SVG copied from Lucide** (ISC), kept as data in
  `src/app/shared/icon/icons.ts`. No icon package dependency.
- **Category chips and roll-ups keep color + icon + text**: a chip shows the category icon and
  label plus the status icon, with the status as screen-reader text and tooltip. Roll-ups list
  counts worst first ("2 not ready, 3 expiring, 18 ready") and hide zero counts.
- **Readiness URL parameters**: `view`, `issues`, `sup`, `prog`, `cat`, `status`, `direct`, `q`.
  Defaults are left out. `prog=all` exists so "All programs" can override a default program
  from Preferences. Unknown or out-of-scope values are ignored rather than shown as errors.
- **Keyword search filters as you type**; the URL catches up after a 300 ms pause (replacing
  the history entry, so Back doesn't step through every keystroke).
- **Clear filters** resets categories, statuses, Direct reports only and the keyword. Scope,
  view and Issues only are kept: they are choices of what to look at, not filters.
- **The tree is a flat list of indented rows** rather than nested components: simpler, and 200
  rows need no virtual scrolling. A much bigger real org would want virtual scrolling.
- **Tree expand state is remembered per query** (root-provided `TreeStateService`, not the
  URL): it survives opening a person and pressing Back, and a new filter starts from the
  default open state.
- **Context rows** (managers kept only to show the path) are dimmed and say "shown for
  context" to screen readers. A matched employee ID is shown on the row only while searching.
- **M4: the Layout switch lives in the avatar menu's Preferences** (user) from M4, next to the
  default scope. M7's presenter panel will reuse it.
- **M4: the Dashboard acts like Drill-down on narrow screens** (user): tapping a person opens
  the full page, since side by side doesn't fit.
- **M4: picking a person in the Dashboard replaces the history entry** (user), so Back leaves
  the Readiness page instead of stepping back through every person looked at.
- **M4: programs are header badges with their own status** (user), e.g. "Crane Operations: Not
  ready". No Programs tile; problem checks stay in their categories, marked "required by".
- **M4: categories with nothing tracked show a greyed "Nothing tracked" tile** (user), with no
  status color, so all 8 tiles line up and it's never read as Unknown.
- **Checks show as a table only on the wide person page.** The dashboard panel and phones get
  stacked cards with the same facts, since nine columns don't fit in a narrow column.
- **Dates read "Dec 1, 2026"**, days left as "12 days" / "Today" / "3 days overdue", and last
  sync as "Today" / "Yesterday" / "9 days ago" (relative to the demo date). Source systems get
  display names from a config table (`SOURCE_LABELS`).
- **The dashboard's open person is the `person` URL parameter** on the Readiness page, so a
  link can open someone directly. Someone the viewer can't see is ignored. Clear filters keeps
  it. Side by side starts at 1024px wide (`DASHBOARD_MIN_WIDTH_PX`).
- **In the dashboard, arrow keys only move focus; Enter or a click opens the person**, so the
  panel doesn't change while moving through the tree. Close (or Escape) puts focus back on the
  person's row.
- **Status reasons use the friendly date format too** ("Valid through Dec 25, 2026"). Cards
  don't repeat a date the reason already names; they say "56 days left" instead.
- **Category tiles size to their container** (CSS container query): four across on the page,
  two across in the narrow panel.
- **M5: undated checks in the list** (user): not ready with no date (missing, lost, revoked)
  sorts to the top with the overdue items, since it blocks work today; other undated checks
  (completed training) go after everything dated. Within each group, worst status first, then item name.
- **M5: a picked program narrows the list to the same people as the tree** (user), with all
  their issue checks, so the list and tree always agree. Rows show "required by".
- **M5: long lists show 100 rows at a time** (user) with "Show 100 more" and "Showing 100 of
  2,140". Filters are the real way to narrow it.
- **M5: one fixed list order, ~~soonest first~~** (user). No column sorting for now; ask users
  in the demo whether they miss it. (Since the 2026-10-31 list by person: worst first, then
  soonest due.)
- **In the list, the person's name is the row's button** (keyboard reachable, Enter opens);
  the whole row is also clickable. With the Dashboard panel open, the manager ~~and category
  columns fold under the person and item~~ folds under the name and cells show icons only
  (2026-10-31, list by person).
- **The tree and list share one empty state** (`ReadinessEmpty`).
- **Don't hide a daisyUI `table` with `hidden md:table`**: the class `table` is also Tailwind's
  `display: table` utility and wins over `hidden`. Hide a wrapper div instead.
- **M6: View as moves into Preferences now** (user), as Layout did in M4; M7's presenter panel
  reuses it. The Admin link and screens show only for the Admin persona; `/admin` tells other
  personas it is for admins.
- **M6: assignments are edited on each program's page** (user), in a People section with add
  and remove, next to the program's requirements.
- **M6: "assign a whole subtree" is a one-time add** (user): everyone under that supervisor now,
  each removable on their own. A standing rule would need a settings schema change and the fake
  org never changes, so the demo couldn't show the difference.
- **M6: the settings file and Admin's Reset cover admin settings only** (user): programs,
  assignments and warning windows. Importing keeps the viewer's own preferences (theme, layout,
  default scope, persona, demo date). M7's demo Reset is the one that clears everything.
- **M6: Thresholds holds only the warning window per category** (user), as DESIGN.md says.
  Device check-in limits and source staleness stay in config while the devices question is open.
- **M6: admin edits save and apply at once**, with no Save button, since the acceptance check
  asks for "immediately" and a draft would mean handling unsaved changes on leaving the page.
- **Program names are unique ignoring case**, and the id is made from the name when the
  program is created (`prog-night-shift`, numbered if taken). Renaming keeps the id, so
  assignments, saved defaults and links survive a rename.
- **Rename saves on Enter or on leaving the field**; Escape puts the saved name back. A bad name
  shows its reason under the field and changes nothing.
- ~~**The requirement picker opens inline** under the requirements, grouped by category with a
  search box, rather than in a dialog, so the list and the live summary stay in view while
  adding several items.~~ (Replaced 2026-10-31 by typed requirements; the typed form also opens
  inline, for the same reason.)
- **Confirmations use a native `<dialog>` (daisyUI `modal`)** through one shared
  `ConfirmDialog`: Escape and Cancel answer no. Specs stub `showModal` (`stubDialogs()` in
  `src/app/testing.ts`) since jsdom has none.
- **Admin screens edit settings only through `AdminService`**, which also drives the "Saved"
  note next to the Admin heading.
- **"Add everyone under" leaves the supervisor off** and adds only people not already on the
  program; the button says how many ("Add 9 people"). The supervisor can be added by search.
- **People search on a program shows at most 8 matches** ("Showing 8 of 23 matches. Keep typing
  to narrow it."), over the whole org since admins see everyone.
- **Pick lists that are rebuilt on every edit keep their selection** (`linkedSignal` with the
  previous value) while it is still a choice; otherwise each assignment reset the supervisor.
- **A warning window applies 400 ms after typing stops**, or at once on Enter or leaving the
  field. A value outside 0 to 3650 whole days shows its reason on the row and changes nothing.
  Typing the default value removes the override, so the settings file only lists real changes.
- **Import reads the file first, then asks**: "mine.json has 5 programs, 61 assignments, 1
  warning window. It replaces the current ...". A bad file shows its readable error and changes
  nothing. Reset also asks, and suggests exporting first.
- **The exported file is named with the (demo) date**, `ready-to-work-settings-2026-10-30.json`.
- **A default program that an import or reset removes is cleared** back to All programs, the
  same as deleting a program.
- **"Add everyone under" starts on "Choose a supervisor"** with the button disabled, so one
  click can't put the whole org on a program (found in the M6 screenshots: it started on the
  admin, offering "Add 186 people").
- **On phones, a program's people rows keep one line**: the title truncates and Remove is an
  icon button (its label stays for screen readers and as a tooltip).
- **Unknown status removed; status is judged by dates only** (user, chose this over folding
  stale data into Expiring or only hiding it in the demo). The grey fourth status confused
  them. Now there are three statuses. A record whose source hasn't synced within its limit
  keeps the status its dates give and shows an "Out of date" note by its last-synced time
  (`Check.stale`, `staleAfterDays` stay in config). A record or person with no data at all is
  Not ready ("No data"), so missing data still never shows green. The seed drops its 3%
  unknown share (now 73% ready) and the grey Yubikey crew scenario, so the demo has no
  out-of-date data; an old `status=unknown` in a URL is ignored. The unused help-circle icon
  went with it.
- **Pages use the full window width** (user: the grids didn't fill the screen). The main area
  no longer stops at 1280px; the tree, list and dashboard stretch with the window. Admin forms
  and explanatory text keep their own narrower widths so fields and lines stay readable.
- **Fake names are common American first and last names** (user: the earlier mix read as too
  exotic). Pairs are random, so they are not real people; the seed now gives different names.
- **Tree issue chips line up in a column** (user: the issues weren't horizontally aligned).
  From the sm breakpoint up, the status badge, name and title sit in a fixed-width column
  (the depth indent is inside it; 22rem, widening to 26, 30 and 34rem at md, lg and xl so the
  admin's five-level tree doesn't wrap names on desktop) and the status badge has a fixed width, so category chips
  start at the same x on every row. When a row is too narrow, the roll-up summary wraps
  first. Phones keep the stacked layout.
- **A tree row click opens and closes the row; a Details button opens the person** (user: the
  main click should expand and collapse). The whole row toggles a manager's branch, so the
  chevron is no longer a separate target. Each row ends with a Details button. It is out of
  the tab order because the row is the tree's one tab stop and Enter on it still opens the
  person. ~~A row with no one under it has nothing to toggle, so clicking it opens the person
  (our default; easy to change to "Details only").~~ (Replaced 2026-10-31: Details only.)
- **A "new version is available" notice with Refresh** (user request). With the service worker,
  a plain refresh first shows the cached old build and only downloads the new one in the
  background, so people think nothing changed; open dashboards may never refresh at all. The
  notice appears when Angular's service worker reports the new build ready (`VERSION_READY`),
  so one Refresh loads it. Also shown if the cached app is broken (`unrecoverable`). Later
  hides it until the next new version. The app checks every 15 minutes (`UPDATE_CONFIG`) and
  when its tab comes back into view. A toast at the bottom right (centered on phones), not a
  banner, so it doesn't compete with the coming announcements banner.
- **Announcements: answers to the plan's questions** (user, 2026-10-30; all recommended
  options). Three types, Outage (red), Delayed (amber) and Info (blue), on a full-width strip
  that looks unlike the status badges. Viewers can close Info and Delayed notices (remembered in
  their preferences, back again after an admin edit); outages can't be closed. Optional start
  and end dates, no times. Edits go live with a Publish button, unlike the rest of Admin. The
  demo starts with one live Delayed notice.
- **Announcements don't change the settings schema version.** Saved settings with no
  `announcements` section already fall back to the defaults, so older saved settings pick up the
  sample notice and no migration is needed (the plan had assumed version 2).

## 2026-10-31

- **Password protection, when we add it, will be basic-auth middleware** (user; not built
  yet). A small `middleware.ts` at the project root checks a username and password held in
  Vercel environment variables before serving any page; the browser shows its own login box.
  Chosen over Vercel's Password Protection (paid add-on), Vercel Authentication (every viewer
  needs a Vercel account on the team) and an in-app password screen (cosmetic only, bypassable
  from the JavaScript). Free on the Hobby plan and a real server-side check.
- **Only the Details button opens a person from the tree** (user). Clicking the row of someone
  with no one under them now does nothing, and only manager rows show the pointer cursor.
  Enter on a row still opens the person, since the Details button is out of the tab order. The
  List view has no Details button and still opens the person on a row click.
- **Change log on its own page** (user). A Change log row in the avatar menu opens
  `/changelog`. It starts empty from today (no backfill), uses dates only (no version numbers),
  has no "new" marker, and groups each day under New, Changes and Fixes. Lines stay short and
  human readable, with no heavy detail. The entries are a typed data file, not Markdown, so no
  parser is needed and a test checks the dates are newest first.
- **List view: one row per person, a column per category** (user; replaces the M5 one row per
  check). The user took the recommended option on all five plan questions: replace the old
  list; a cell shows the worst status plus the soonest days left; ready categories show as
  green cells even with Issues only on; picked categories hide the other columns; with the side
  panel open, cells show icons only. Two follow-ons: the list now shows exactly the tree's
  people (including someone with no records, all dashes), so the count line is the tree's
  "N of M people shown"; and the keyword no longer matches item names, since rows are people.
- **Shipyard sample data** (user). Programs are shipbuilding programs: one ship on larger
  builds (Ridgeline R-01, R-02, Bastion B-01), the whole class on smaller, modular ones
  (Kestrel, Tern, Harrier). All invented, with no real class names or hull numbers. Titles,
  trainings, qualifications and tools now read like a shipyard. The app doesn't decide ship
  versus class: the real app will get the program list from elsewhere, so it's only in the
  name, with no field for it. No settings upgrade: only the user has opened the demo, and Admin
  › Settings file › Reset to defaults loads the new programs.
- **Requirements are typed IDs, with "any of"** (user). An admin types a course ID, qual ID or
  role name in a plain text box (no suggestions; admins know their systems), and can list
  several IDs where any one fulfills the requirement. A program's requirements together stay
  "all of". Network account and SAP password stay addable, since some programs may not use
  computers. Details wait on the second round of questions in plans/typed-requirements.md.
- **Typed requirements, second round** (user). One "any of" can mix types (for example a course
  or a qualification), for flexibility. Any requirement can have a name; none needs one. IDs
  match ignoring case and surrounding spaces. The sample data starts with network account and
  SAP password required where the work uses computers; from scratch, a program requires nothing
  until an admin adds it. The fixed catalog behind the old picker is gone; item names for labels
  and the "no records with this ID" note come from the records themselves. Older saved settings
  (one item per requirement) still load, as one-option requirements.
- **Program assignment in the real app** (user, future): probably by who you work for ("you work
  for X, so you get their program") rather than one by one. Noted for later; the mockup keeps
  per-person assignment.
- **Saved settings upgrade to version 2** (user: "resolve it, not reset by hand"; replaces the
  earlier "no settings upgrade" call). Settings saved before the shipyard programs (version 1)
  load with their programs, assignments and default program dropped, so the new sample
  programs appear; thresholds, announcements and other preferences are kept. The step is a
  reusable `replaceSamplePrograms` migration, to add again whenever the sample programs change
  (noted in CLAUDE.md). An exported version 1 settings file imports the same way.
- **AGENTS.md points to CLAUDE.md** (user). AGENTS.md, the file other coding assistants read,
  is a one-line pointer so the project instructions have a single copy in CLAUDE.md.
- **A person's items open in place, in the tree and the list** (user: "expand an individual to
  see what they are missing"). The recommended options: issues first with "Show all N items";
  both views. No keyboard shortcut for it (user: no specific key press should control
  anything); the toggle is a plain button out of the tab order like Details, and Enter on a row
  still opens Details. Open items are remembered while switching views. The due-line wording
  and which item IDs to show moved into the core so Details and the inline view match.
- **Export to CSV** (user: "export to Excel, likely just CSV"; the plan's recommended options).
  One row per person, exactly the people the page shows under the current filters, a "Reports
  to" column instead of the tree's context rows, the same file from both views. Each category
  gets two columns (status, days left) so Excel can filter on status. Plain CSV built in the
  core, no library; values that would start a spreadsheet formula get an apostrophe.
- **General Foreman persona** (user). Added to View as, between Foreman and Superintendent: the
  tool crew foreman's own general foreman, so the demo can walk one chain upward.
- **Crews by trade** (user). Each superintendent's people are one trade; only the crew level
  gets trade titles, with the odd person on loan from another trade (5%). Foreman and above
  keep their titles. Qualifications generally follow the trade (85% hold their trade's qual,
  plus sometimes a general one: crane, rigging, competent person, fire watch). Four trades, one
  per superintendent, since the user didn't pick a different set; two new trade quals
  (Pipefitter Certification, Shipfitter Certification). The regenerated org changes the
  default assignments, so saved settings go to version 3 with the same sample-program upgrade.
- **Trade-specific quals within a program** (user, future): a program may later need different
  qualifications per trade. Not built.
- **Department per person** (user): planned, then put on hold to do trades first. The draft is
  plans/department.md.
- **Search ignores Issues only** (user). A ready person showed in the tree as context but the
  search couldn't find them. While there is a keyword, Issues only and its category and status
  filters pause; the switch says so, the filter buttons are disabled, and clearing the search
  restores them. The rule is one core function (`issuesFilterApplies`).
- **No sideways page scroll on the Readiness page** (user). The tree/list box is a grid item,
  which grew to the table's width; it now has `min-w-0` and the table scrolls inside its own
  box when it must. Below 2xl the list folds the manager under the name, like the panel view.
- **Cleanup pass** (user: "clean up documentation, look for tech debt or duplicative code").
  Shared helpers replace repeated code: `categoryConfig` and `countText` in the core,
  `downloadFile` for both downloads, `SettingsService.programNames`, and one `ItemsToggle`
  component for the tree, list and phone cards. Docs brought in line with what is built;
  replaced decisions above are marked.
- **Dismissing announcements is probably a mistake** (user, for later): viewers can close Info
  and Delayed notices today; the user expects to remove that. Noted in Tasks.md; not changed.
